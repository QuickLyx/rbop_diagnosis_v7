## 5. 跑全批：train → eval

```bash
nohup bash scripts/run_cloud.sh all > logs/cloud_all.log 2>&1 &
tail -f logs/cloud_all.log        # 或另开终端：bash scripts/run_cloud.sh status
```

`all` = `check` + `train` + `eval`。单格失败**不中断整批**（失败格记录在 `logs/failed_train.txt` / `logs/failed_eval.txt`，其余格继续）。中断后重跑同一命令即续上：已有 `last.pt` 的格、已有 `metrics.json` 的评估自动跳过；失败格残留目录挪到 `<cell>_failed_<时间戳>` 留现场，不删。

两个硬性顺序（`train` 内部已自动处理，手动拆跑时必须遵守）：

1. **12 个 joint 全部完成后才能跑 84 个后续臂**：后续臂的 checkpoint 校验（`validate_source_checkpoint`）要求同折同种子 joint 的 `epoch=checkpoint_epoch=last_epoch=30`，中断的 joint 末轮会被拒绝；
2. **评估在训练之后**：`evaluate.py` 只接受完整 30 轮的 `last.pt`。

拆开跑也行：

```bash
bash scripts/run_cloud.sh check
nohup bash scripts/run_cloud.sh train > logs/train.log 2>&1 &
# 训练 96/96 完成后：
nohup bash scripts/run_cloud.sh eval > logs/eval.log 2>&1 &
```

并行度用环境变量控制：`PAR=2 bash scripts/run_cloud.sh train`（默认 2，见 §6）。

## 6. 并行与两个 GPU 怎么选

### 先回答：脚本可以并行吗？

**可以，且不影响结果。** 依据：

- 每格是**独立进程**：`run_cloud.sh` 用 `xargs -P $PAR` 分发，每格一次 `python train.py` 调用，独立固定种子（`seed_everything`，含 `cudnn.deterministic=True`）；
- 格间无共享状态：各自的输出目录、各自的 DataLoader，唯一共享的是只读的特征缓存（`np.memmap` 只读映射，多进程并发读安全）和同一块 GPU 的算力；
- GPU 上的核函数按流调度，一个进程的 kernel 不会改变另一个进程的计算结果（CUPTI/cuDNN 逐位确定性在同一 GPU 型号 + 同一进程内成立；跨进程并行不改变每格进程内部的归约顺序）。
- 结果可比性口径（沿用 v6 说明 §8）：不同 GPU 型号之间逐位不一致是本来就有的事，与并行无关；要求的是**同一台机器、同型号 GPU 内**同 fold/seed 可重复。**要比较 T4 与 A10 的结果或混用两台工作区时注意：跨型号不保证逐位一致，整批最好固定在同一种 GPU 上跑完。**

### T4 vs A10（价格：T4 1.2、A10 3.3 机时/小时）

| | T4（16GB / 8 核） | A10（24GB / 20 核） |
| --- | --- | --- |
| 单进程显存占用 | <2 GB，16GB 富余 | 同左，24GB 更富余 |
| 单进程 GPU 利用率 | 低（小模型 + LSTM 逐步推理，估计 30–50%） | 更低（算力更强，喂数据的问题更明显） |
| 实用并行数 PAR | 2–3（受 8 核 CPU 限制） | 3–4（20 核，CPU 不是瓶颈） |
| 单格时长（估） | joint ≈ 5–7 分钟；带目标臂 ≈ 8–12 分钟 | joint ≈ 2–3 分钟；带目标臂 ≈ 3–5 分钟 |
| 96 格总 wall time（估） | PAR=2：约 8–10 小时 | PAR=3：约 2.5–3.5 小时 |
| 总机时消耗（估） | 9h × 1.2 ≈ **11 机时** | 3h × 3.3 ≈ **10 机时** |

**结论**：

- **两边总机时差不多（≈10–11 机时）**，因为并行省下的时间就是价格贵出来的倍数，基本抵消；
- **A10 更划算的地方是墙钟时间**：3 小时出结果 vs 9 小时，交互迭代（第一次跑要排错）价值很大；且 20 核 CPU 让 PAR=4 也稳；
- **T4 更划算的场景**：一次跑通不需要迭代、且你能挂着过夜——省心省钱差不多；
- **推荐**：第一次用 **A10 + PAR=3** 跑全批（快速拿到结果、排错成本低）；跑顺了若还需要补跑/重跑，用 T4 挂夜即可。
- 以上时长是**按 v6 实测（400 步/轮 ≈ 4 分钟/格 @1650Ti）与 v7 步数（400 步/轮 × 30 轮 = 12,000 步/格）折算的估算**，不是承诺值；真实速率开跑第一个 joint 后即可从日志的"耗时 N 秒"校准，`status` 看进度。

## 7. 失败与重跑

- 单格失败不中断整批，失败格名单在 `logs/failed_train.txt` / `logs/failed_eval.txt`；整批结束后 `status` 会点名。
- 重跑同一命令（`train` 或 `eval`）即自动重试失败格、跳过已完成格，无额外开关。
- `train.py`/`evaluate.py` 拒绝写入非空目录：脚本已自动把失败残留挪到 `_failed_<时间戳>`，不覆盖任何产物。
- 只有一个格反复失败时才去看它的报错与 `_failed_*` 目录里的 `history.csv`（跑到第几轮），不要动别处。
- **云端不要用 `scripts/run_matrix.sh`**：它默认 dry-run（本地预检用），且是顺序单进程，没有 `run_cloud.sh` 的并行与续跑能力。

## 8. 云端不要做的三件事

1. **不要重跑 `selection.py`**：池是冻结的协议组件，`selection.json` 已随仓库带齐；sklearn 版本差异可能给出不同簇，那才是破坏可比性的事。`check` 的 dry-run 会核对 k=19、嵌套池、153/116 口径。
2. **不要提交 `outputs/train/`（约 300 MB 权重）与 `logs/`**（`.gitignore` 已排除）。跑完把 `outputs/eval/`（约 50–100 MB，不含权重，108 份 × 4 文件）拉回本地或推回仓库。
3. **不要改判据、预算、配对链、折数或种子**：改了 `configs/stage2.json`，`train.py` 的 `_check_frozen` 直接报错拒绝运行。结果未达标时按 `agents.md` 的零算力错误结构分析走，不临时加臂。

## 9. 跑完之后

- `bash scripts/run_cloud.sh status` 应打印 `训练：96/96 格完成`、`评估：108/108 份完成`；
- 每格 `outputs/eval/<cell>_paderborn/metrics.json` 的 `D3` 字段即该格判据结果（`passed: true/false`，全 116 单元宏平均 E1/E2）；单格通过与否**不等于**最终结论——最终判据与六对配对链比较要 96 格全齐后在本地统一汇总（工程简单原则，云端不写汇总脚本）；
- 回传内容：`outputs/eval/` 整目录 + `outputs/train/*/history.csv`（训练曲线）。权重 `last.pt` 视需要带回（每格约 1–3.5 MB × 96）。
